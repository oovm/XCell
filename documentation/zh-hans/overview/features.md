# XCell 功能特性

## 现有功能

### 多种表格类型
- **Class 表**：定义结构化的数据类，包含字段定义和数据行
- **Dictionary 表**：键值对数据存储，支持列表和字典两种形式
- **Enumerate 表**：定义枚举类型和枚举值
- **Language 表**：多语言文本管理

### 合表功能
- **行合并 (Row Merge)**：将多个具有相同结构的表格按行合并
- **列合并 (Column Merge)**：将多个表格按列合并

### 导出功能
- **Unity (C#) 导出**：自动生成强类型的 C# 类和数据管理器
- **二进制导出**：高效的二进制数据格式，支持大小端配置
- **XML 导出**：标准的 DataContract 格式，易于调试和查看
- **JSON 导出**：通用的 JSON 格式，便于 Web 应用和跨平台使用

### 配置系统
- **项目配置 (ProjectConfig)**：工作目录设置、文件包含/排除规则、输出目录配置
- **表格配置 (TableConfig)**：表格特定的配置选项、行模式配置
- **游戏引擎配置**：Unity 配置、其他引擎配置

### 技术特性
- **Rust 编程语言**：高性能、内存安全、并发安全、跨平台
- **模块化架构**：核心功能库、数据类型定义、错误处理系统、命令行界面、图形用户界面
- **类型系统**：丰富的内置数据类型、自定义类型支持、严格的类型检查
- **增量监听模式**：使用文件系统监听，只处理修改过的文件
- **模板引擎**：使用 Askama 模板引擎，编译时模板检查

## 计划添加的功能

### 1. 基于文件事件的过期检测
- **功能描述**：监控配置文件的修改事件，检测过期的配置数据，并提供通知机制
- **实现方式**：利用现有的文件系统监听机制，标记过期的配置数据
- **使用场景**：当配置文件被修改时，系统会自动检测相关配置是否过期，并通知用户
- **工作原理**：
  - 系统会记录每个配置文件的修改时间
  - 当检测到文件变更时，会比较修改时间
  - 如果文件被修改，系统会标记相关配置为过期状态
  - 系统会自动重新加载过期的配置文件
  - 重新导出相关的代码和数据

### 2. 数据验证检查

#### 2.1 Ref 检查
- **功能描述**：验证配置中的 ID 引用是否存在
- **使用场景**：确保配置中引用的 ID 在目标表格中存在，避免运行时错误
- **实现方式**：
  - 分析配置中的 ID 引用
  - 检查引用的 ID 是否在目标表格中存在
  - 如果引用不存在，系统会报错

#### 2.2 Path 检查
- **功能描述**：验证资源路径是否有效
- **使用场景**：确保配置中指定的资源路径存在，避免运行时资源加载错误
- **实现方式**：
  - 分析配置中的资源路径
  - 检查路径是否存在
  - 如果路径不存在，系统会报错

#### 2.3 Range 检查
- **功能描述**：验证数值是否在合理范围内
- **使用场景**：确保配置中的数值在预期范围内，避免异常值导致的问题
- **实现方式**：
  - 分析配置中的数值字段
  - 检查数值是否在指定范围内
  - 如果数值超出范围，系统会报错

#### 2.4 一致性检查
- **功能描述**：验证跨表格数据的一致性
- **使用场景**：确保多个表格之间的关联数据保持一致，避免数据冲突
- **实现方式**：
  - 分析跨表格的关联数据
  - 检查关联数据是否一致
  - 如果数据不一致，系统会报错

### 3. 条件导出功能
- **功能描述**：支持基于配置的条件导出，使用 TOML 配置文件控制导出条件
- **使用场景**：区分 server 表和 client 表的导出，只导出符合特定条件的表格
- **配置方式**：通过 TOML 配置文件定义导出条件
- **配置示例**：
  ```toml
  [export_conditions]
  [[export_conditions]]
  table_pattern = "Server*"
  target = "server"
  
  [[export_conditions]]
  table_pattern = "Client*"
  target = "client"
  
  [[export_conditions]]
  table_pattern = "*"
  target = "both"
  ```
- **工作原理**：
  - 系统会根据配置文件中的条件判断表格是否应该导出
  - 对于每个表格，系统会检查是否符合导出条件
  - 只有符合条件的表格才会被导出

### 4. 插件系统
- **功能描述**：设计插件架构，支持插件的加载和管理，提供插件 API 和扩展点
- **使用场景**：允许用户扩展 XCell 的功能，如添加自定义验证规则、导出格式等
- **设计原则**：保持轻量级，避免过度复杂，提供清晰的 API 接口
- **插件 API**：
  - `initialize`：初始化插件
  - `on_table_load`：表格加载前事件
  - `on_table_loaded`：表格加载后事件
  - `on_export`：导出前事件
- **使用示例**：
  ```rust
  struct MyPlugin;
  
  impl Plugin for MyPlugin {
      fn name(&self) -> &str { "MyPlugin" }
      
      fn initialize(&mut self, workspace: &WorkspaceManager) -> XResult<()> {
          // 初始化插件
          Ok(())
      }
      
      fn on_table_load(&self, table: &CalamineTable) -> XResult<()> {
          // 表格加载前处理
          Ok(())
      }
      
      fn on_table_loaded(&self, table: &CalamineTable) -> XResult<()> {
          // 表格加载后处理
          Ok(())
      }
      
      fn on_export(&self, workspace: &WorkspaceManager) -> XResult<()> {
          // 导出前处理
          Ok(())
      }
  }
  ```

## 技术实现考虑

- **性能**：数据验证检查不应显著影响导出性能，插件系统应保持轻量级
- **可扩展性**：插件系统应易于扩展和定制，数据验证规则应支持自定义
- **兼容性**：新功能应与现有功能兼容，不应破坏现有的配置文件格式

XCell 团队致力于持续改进和扩展工具功能，为游戏开发和复杂数据管理项目提供更全面、更可靠的配置表管理解决方案。
